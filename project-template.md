### Контекст и пользователи

Продукт разрабатывает команда из двух студентов. Пользователь — человек, который хочет вести личный учёт трат, не отдавая данные третьим лицам. Для пользователя важны: сохранность записей, приватность сумм и заметок, быстрый доступ к статистике. Решение о выпуске принимает команда, опираясь на результаты проверок и остаточные риски.

### Границы

**В проект входит:**

- добавление, редактирование и удаление траты;
- категории: предустановленные и пользовательские;
- список трат с фильтром по дате и категории;
- статистика: сумма за период и разбивка по категориям;
- блокировка приложения по Face ID / Touch ID;
- автоблокировка при уходе в фон;
- экспорт данных в CSV по инициативе пользователя;
- снижение риска утечки через скриншоты и запись экрана (маскировка сумм, предупреждение).

**За пределами проекта:**

- сервер, синхронизация, аккаунты;
- интеграция с банками;
- мультивалютность с онлайн-курсами;
- социальные функции;
- аналитика и реклама;
- публикация в App Store;

### Компоненты, взаимодействия и границы доверия

- **UI (SwiftUI)** — ввод и отображение трат.
- **Локальное хранилище (SQLite / Core Data)** — основная база данных.
- **Keychain** — хранение ключа шифрования и PIN.
- **LocalAuthentication** — Face ID / Touch ID.
- **FileManager + UIActivityViewController** — экспорт CSV.
- **Резервное копирование ОС** — потенциальный канал утечки.
- **SceneCaptureState / userDidTakeScreenshotNotification** — детектирование записи экрана и скриншотов.

Границы доверия: UI и хранилище — внутри доверенной зоны приложения; экспортированный файл, скриншот и резервная копия — за пределами доверенной зоны. Сетевых взаимодействий нет.

### Активы и существенные риски

- **Актив:** суммы и категории трат.  
  **Что может произойти:** чтение файла БД при физическом доступе к контейнеру; попадание в скриншот или запись экрана.  
  **Почему это существенно:** раскрывает финансовое поведение пользователя.

- **Актив:** ключ шифрования БД.  
  **Что может произойти:** извлечение из кода или `UserDefaults`.  
  **Почему это существенно:** обесценивает шифрование БД.

- **Актив:** экспортированный CSV.  
  **Что может произойти:** остаётся в общей папке, доступен другим приложениям.  
  **Почему это существенно:** данные покидают защищённый контейнер.

## 2. Методологическая основа

**Основная рамка:** OWASP MASVS 2.0 (Mobile Application Security Verification Standard)  
**Дополнительные источники:** OWASP MASTG, Apple Platform Security Guide, Apple Developer Documentation: Detecting screen capture

**Почему выбрана эта основа:** MASVS покрывает именно мобильные приложения и содержит применимые категории для локального хранения, аутентификации, приватности и качества кода.  
**Что ещё рассматривали:** NIST SSDF — слишком общий для маленького мобильного продукта; OWASP ASVS — ориентирован на веб.

Применимые положения MASVS и их превращение в действия:

- **MASVS-STORAGE** — требует защищать чувствительные данные в локальном хранилище.  
  Применимо: БД содержит суммы и заметки.  
  Действие: шифрование БД, ключ в Keychain.  
  Критерий выполнения: файл БД нечитаем без ключа.

- **MASVS-AUTH** — требует защиты доступа к приложению.  
  Применимо: приложение показывает личные данные.  
  Действие: Face ID / Touch ID и автоблокировка.  
  Критерий выполнения: без биометрии данные недоступны.

- **MASVS-CODE** — требует корректной обработки ошибок и качества кода.  
  Применимо: импорт CSV и валидация ввода.  
  Действие: валидация входных данных, обработка ошибок.  
  Критерий выполнения: некорректный CSV не ломает приложение.

Категории MASVS-NETWORK и MASVS-PLATFORM-INTERACTION применяются ограниченно, так как сети и внешних взаимодействий нет.

**Ограничение платформы:** Apple не предоставляет публичного API для полной блокировки скриншотов. Поддерживаемое решение — детектирование активного захвата экрана и реакции на факт скриншота. Это фиксируется как ограничение и влияет на формулировку обещаний выпуска.

## 3. Текущее состояние

Продукт разрабатывается двумя студентами в общем репозитории.

### Существенные разрывы

- **Разрыв:** БД SQLite хранится в открытом виде.  
  **Почему важен:** любой с доступом к контейнеру читает все траты.

- **Разрыв:** ключ шифрования (если есть) лежит в коде или `UserDefaults`.  
  **Почему важен:** ключ извлекается, шифрование обесценивается.

- **Разрыв:** нет биометрии и автоблокировки.  
  **Почему важен:** любой, взявший телефон, видит данные.  

  **Разрыв:** суммы трат видны на скриншотах и при записи экрана.  
  **Почему важен:** пользователь может случайно поделиться скриншотом или записью, не осознавая, что раскрывает финансовые данные. 

- **Разрыв:** экспорт сохраняет CSV в общую папку.  
  **Почему важен:** файл остаётся доступен другим приложениям.  

## 4. Целевой Secure SDLC

Для каждого выпуска команда проходит четыре контрольные точки (КТ). Следующая КТ начинается только после прохождения предыдущей. Если критерий не выполнен, изменение возвращается на доработку и КТ повторяется на новом коммите. Критерии опираются на контроли MASVS из раздела 2.
 
**КТ-1. Уточнение изменений и затронутых рисков** — перед началом работы над изменением.  
**Что делаем:** в issue автор отмечает, какие компоненты затронуты (хранилище, Keychain, биометрия, экспорт, захват экрана), пересекают ли данные границу доверия и какие контроли MASVS применимы (STORAGE, CRYPTO, AUTH, PLATFORM, CODE). Второй участник подтверждает оценку.  
**Критерий прохождения:** для изменения определены затронутые риски из раздела 1 и перечислены проверки, которые нужно выполнить в КТ-2 и КТ-3.  
**Свидетельство:** issue с заполненным блоком «Влияние на безопасность».
 
**КТ-2. Взаимный review** — на каждом pull request в `main`.  
**Что делаем:** CI запускает сборку, unit-тесты и SwiftLint. Ревьюер (не автор) проверяет код по затронутым рискам: ключ не лежит в коде и `UserDefaults`, запись Keychain создаётся с `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, данные не показываются до успешной биометрии, суммы не пишутся в логи, ввод валидируется.  
**Критерий прохождения:** CI зелёный, нет новых предупреждений Xcode Static Analyzer, нет открытых блокирующих замечаний, PR одобрен вторым участником. Прямые коммиты в `main` запрещены защитой ветки.  
**Свидетельство:** PR с approve и результатом CI.
 
**КТ-3. Тесты, зависимости и состав выпуска** — перед созданием тега, на зафиксированном коммите-кандидате.  
**Что делаем:**
- *Security-регрессия (Карина):* файл БД в контейнере не читается без ключа; приложение без биометрии не показывает данные и блокируется при уходе в фон; при записи экрана суммы замаскированы, после скриншота показывается предупреждение; в снимке переключателя приложений сумм нет; CSV удаляется из временной папки после экспорта.
- *Функциональная регрессия (Григорий):* добавление, изменение, удаление трат, фильтры и статистика работают; данные сохраняются после перезапуска.
- *Зависимости и сборка (Григорий):* версии из `Package.resolved` проверены по базам уязвимостей; собранный `.ipa` проверен MobSF; зафиксирован состав выпуска (SHA, версии Xcode и зависимостей, хэш сборки).
Второй участник повторяет ключевые проверки на своём устройстве или симуляторе.  
**Критерий прохождения:** все security- и функциональные проверки дали ожидаемый результат у обоих участников; нет зависимостей с уязвимостями High/Critical; все находки MobSF уровня High прошли триаж (раздел 7); сборка воспроизведена вторым участником.  
**Свидетельство:** `evidence/release/` — чек-лист проверок со скриншотами и видео (только тестовые данные), отчёты MobSF и SwiftLint, манифест выпуска.
 
**КТ-4. Решение о выпуске** — после КТ-3.  
**Что делаем:** команда сверяет, что все PR выпуска прошли КТ-1 и КТ-2, а КТ-3 выполнена на финальном коммите. Для каждого риска из раздела 1 фиксируется статус: закрыт, частично закрыт или открыт.  
**Критерий прохождения:**
- *выпускать* — все критерии КТ-1–КТ-3 выполнены;
- *выпускать с условиями* — остались неблокирующие проблемы, у каждой есть ответственный и срок;
- *отложить* — БД не зашифрована, ключ доступен вне Keychain или не работает блокировка.
Ограничения платформы (скриншот нельзя запретить полностью) указываются в описании выпуска.  
**Свидетельство:** решение в разделе 9, тег `v1.0` на проверенном коммите.
 
**Распределение ролей.** Карина ведёт security-проверки (КТ-3) и чек-лист security на review. Григорий ведёт CI, зависимости, сборку и состав выпуска. Изменение одного участника принимает второй; ни одна КТ не считается пройденной только по свидетельству её ведущего.

## 5. Технологический профиль

### Метод 1: Статический анализ iOS-приложения

**Риск или свойство:** хардкод секретов, небезопасные API, ошибки конфигурации.  
**Цель:** найти проблемы в коде и конфигурации до запуска.  
**Область проверки:** исходный код, `Info.plist`, entitlements, собранный `.ipa`.  
**Этап жизненного цикла:** перед мержем и перед выпуском.  
**Способ или инструмент** SwiftLint , Xcode Static Analyzer, MobSF (Mobile Security Framework.  
**Ведущий участник:** Пустовалов Григорий.  
**Как партнёр проверит результат:** запускает те же инструменты на том же коммите и сверяет отчёт.  
**Ожидаемые свидетельства:** отчёт MobSF, вывод SwiftLint, скриншот Xcode Analyzer.  
**Что метод не покрывает:** runtime-поведение, логику приложения, утечки через UI и захват экрана.

### Метод 2: Ручная проверка локального хранилища и приватности

**Риск или свойство:** данные в открытом виде, скриншоты, запись экрана, экспорт.  
**Цель:** подтвердить, как данные лежат на устройстве и не утекают ли наружу.  
**Область проверки:** контейнер приложения, Keychain, экспортированный CSV, активная запись экрана и скриншоты.  
**Этап жизненного цикла:** перед выпуском и после улучшения.  
**Способ или инструмент и версия:** ручное тестирование/автотестирование. Через системные настройки, встроенная запись экрана iOS (Пункт управления → Запись экрана).  
**Ведущий участник:** Самсонова Карина.  
**Как партнёр проверит результат:** повторяет шаги на своём устройстве/симуляторе и сверяет скриншоты.  
**Ожидаемые свидетельства:** скриншоты БД до и после шифрования, скриншоты и запись экрана до и после маскировки.  

У каждого участника есть собственный содержательный участок работы; партнёр проверяет значимую часть результата.
